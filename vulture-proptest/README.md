# Property-based test harness

Live validation for `vulture`'s RAPTOR implementation: random transit
networks generated by [Hegel](https://github.com/hegeldev/hegel-rust)
are run through both `vulture::Timetable::raptor` and a brute-force
reference solver, and the outputs compared. Runs as part of `cargo
nextest r` on every commit.

For the wider testing strategy (unit tests, doctests, where this
harness fits) see the *How Vulture is tested* section in the
top-level [`README.md`](../README.md).

## Properties

Six `#[hegel::test]` properties live in [`src/lib.rs`](src/lib.rs):

| Property | Invariant |
| --- | --- |
| `layer1_matches_reference` | At Layer 1 (no footpaths), vulture's Pareto front equals the reference solver's, on `(arrival, trip_count)`. |
| `layer2_matches_reference` | Same, with footpaths added. Stresses the Dijkstra footpath-relaxation path and journey reconstruction through walk legs. |
| `layer3_matches_reference` | Same, with multi-source / multi-target queries (1–3 origins and 1–3 targets, each a `(stop, walk_offset)` pair). 500 cases per run. |
| `parallel_naive_matches_serial_rrap` | Serial rRAPTOR (`.run()`), `.run_par()`, and `.run_with_pool()` produce byte-identical Pareto profiles for the same range query. Catches both rRAPTOR-specialisation bugs and parallel-batch races. |
| `range_query_matches_reference` | Range-query output equals an independent brute-force reference: per-`τ` solve plus the same 3-D Pareto filter (`later depart, fewer transfers, earlier arrival`) vulture's `filter_range_pareto_front` uses. |
| `fare_label_matches_per_leg_sum` | The `ArrivalAndFare` label's accumulated `fare` equals the manual per-leg sum of route fares for every returned journey. Validates that the `Label::Ctx`-threaded `extend_by_trip` keeps fare state in sync with the plan. |

## Generator layers

Specs are drawn at one of three difficulty layers, each tuning what
the random generator can sample:

| Layer | Stops | Routes | Trips/route | Footpaths | `max_transfers` | Extras |
|-------|-------|--------|-------------|-----------|-----------------|--------|
| 1     | 2..=4 | 1..=2  | 1..=2       | 0         | 1..=5           | – |
| 2     | 2..=5 | 1..=3  | 1..=2       | 1..=4     | 1..=5           | – |
| 3     | 2..=6 | 1..=8  | 1..=4       | 0..=8     | 1..=7           | per-route fares (0..=200), accessibility flags, loop routes |

Multi-source / multi-target queries (1–3 origins and 1–3 targets,
each with an optional walk offset 0..=20 s) are drawn at every
layer; the brute-force reference solver mirrors by seeding Dijkstra
from every origin and applying the Pareto filter across every target.

Layer 3 also allows loop routes: a single route's `stop_sequence`
may revisit the same stop. The reference solver iterates by position
within the trip's schedule rather than by stop id, so the position-
aware `Timetable` accessors (`stop_at`, `get_arrival_time(trip, pos)`)
are exercised against ground truth.

## Conventions

### Trip-count, not transfer-count

`Timetable::raptor`'s `transfers` parameter is the trip count, not the
transfer count, despite its name. A journey "board R1 to B, board R2
to D" has 2 trips and 1 transfer; `transfers=2` admits this journey.
`Journey::plan.len()` is the trip count too. The Pareto front compared
in property tests is over `(arrival, trip_count)`.

### Empty-plan convention (`k == 0`)

`reconstruct_journey` filters out empty plans (no boarding events),
so RAPTOR cannot emit a `k == 0` journey. The reference solver
matches this in two cases:

- `ps == pt` ("stay put"): early-return empty front.
- `ps != pt` walk-only: the final filter drops journeys with
  `k == 0`.

Either way, "no transit boarding involved" is not modelled as a
journey.

### Trips on a route share leg/dwell durations

The generator constrains trips on the same route to share
`leg_durations` and `dwell_times`, making overtaking *structurally
impossible* — every spec the generator produces is a valid RAPTOR
input. This is stricter than the paper requires (which allows
differing durations as long as no trip overtakes another), so the
harness samples a smaller subset of valid networks. Loosening this
is a future enhancement; expect ~20–30 lines of changes in
`route_spec` plus an explicit no-overtaking check in `render`.

## Reproducing a failure

Hegel persists shrunk failing seeds to `.hegel/` (gitignored).
Re-running

```sh
cargo nextest r -p vulture-proptest <test_name>
```

deterministically reproduces the most recent shrunk counterexample.
To reproduce a specific failure on another machine, pin the seed:

```rust
#[hegel::test(seed = Some(0xdeadbeef))]
fn layer2_matches_reference(tc: hegel::TestCase) { /* ... */ }
```

## Adding a new generator layer or property

1. Add a `LayerBounds` constant via `layerN_bounds()` in
   [`src/spec.rs`](src/spec.rs).
2. Add a `#[hegel::test]` function in [`src/lib.rs`](src/lib.rs)
   that draws from `spec::network_spec(spec::layerN_bounds())` and
   asserts whatever invariant you want to check. For
   front-equality properties, lean on `run_property` (see existing
   layers for the call shape).
3. If the new layer requires multi-criterion comparison, the
   property helper (`run_property`) and `raptor_front` will need to
   be generalised — current shape is fixed to single-criterion
   `ArrivalTime`.
